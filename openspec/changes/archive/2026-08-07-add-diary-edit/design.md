## Context

기존 `diary-write`는 각 기록을 `{ date, time, text, createdAt }`로 localStorage 배열에 저장하고, `createdAt` 내림차순으로 목록을 렌더링한다. See proposal.md - Why.

## Goals / Non-Goals

**Goals:**
- 목록 항목을 식별하고 텍스트만 갱신하는 방법을 정한다
- 인라인 편집 상태를 렌더링 로직에서 어떻게 표현할지 정한다

**Non-Goals:**
- 삭제 기능 (이번 change 스코프 밖)
- 수정 시각 기록/이력 관리 (스코프 밖)

## Decisions

- **항목 식별자**: 기록에 `id`(예: `createdAt` 값 자체, 또는 별도 증가 카운터) 필요. `createdAt`은 밀리초 단위라 동일 세션에서 연속 저장 시 충돌 가능성이 낮지만 완전히 배제할 수 없으므로, 저장 시 `id: crypto.randomUUID()`를 함께 부여해 항목을 고유하게 식별한다. 기존 데이터(旧 레코드)에는 `id`가 없을 수 있으므로 로드 시 `id`가 없는 레코드에는 `index` 기반 임시 id를 부여해 하위 호환을 유지한다.
- **인라인 편집 상태 관리**: 별도의 "편집 중인 항목 id"를 모듈 스코프 변수로 유지하고, 렌더링 시 해당 id의 항목만 입력 필드 + 저장/취소 버튼으로 렌더링한다. React 등 프레임워크 없이 Vanilla JS로 매번 전체 목록을 다시 그리는 기존 패턴(`renderEntries`)을 그대로 재사용한다.
- **저장 시 갱신 범위**: 텍스트만 교체하고 `date`/`time`/`createdAt`은 그대로 둔다 - 정렬 기준이 `createdAt`이므로 순서가 보존된다.
- **빈 값 처리**: 기존 저장 로직과 동일하게 trim 후 빈 문자열이면 갱신하지 않고 인라인 편집 상태를 유지한다(사용자가 다시 시도할 수 있도록).

## Risks / Trade-offs

- [id 없는 기존 레코드] 이전 change에서 저장된 레코드에는 `id`가 없다 → 로드 시 `index` 기반 임시 id로 보완하지만, 같은 세션 내 저장 순서가 바뀌면(예: 필터링) 임시 id가 흔들릴 수 있음. 다만 이번 change는 필터링 기능이 없어 실질적 위험은 낮음.
- [인라인 편집 중 목록 갱신] 편집 중 다른 항목을 저장하면 전체 목록이 다시 그려지며 편집 상태가 유지되도록 렌더링 시 "편집 중인 id"를 기준으로 다시 입력 모드로 그려야 함 - 누락 시 편집 내용이 사라질 수 있음.
